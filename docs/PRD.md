版本：0.79（2026-10-27）  
状态：需求研究 MVP；真实 GitHub 采集曾在可信 TLS 环境通过，本机当前预检仍受网络认证/证书链阻断；候选运行与独立用户收益尚未全面验证。

## 1. 产品要解决的问题

用户想实现一个需求，但不知道有哪些开源项目、能否直接运行，以及改造一个项目与组合多个项目哪个更合适。产品应减少从需求到可核查实现路径的研究和试错成本。

输入自然语言需求，输出真实候选、依据、缺口和下一项可执行验证。社会模拟游戏是验收案例之一。项目本身是研究和选型助手，范围不扩展为社会模拟游戏引擎。

项目雷达、机会发现和共享资料继续保留；当前演进以需求研究为主，不以持续生成组合报告作为成果。

首页必须把“从需求开始”作为首个行动入口：用户无需先理解扫描、机会或能力分类，就能直接进入自然语言需求研究；项目雷达作为后续证据工作台保留。首页入口需说明三步路径（描述目标、核查版本、运行最小实验），并在桌面与 390px 窄屏可见、可操作。

首页右上角的主操作必须与首屏入口一致，显示“开始需求研究”并进入 `/research`；GitHub 扫描操作保留在非研究页面或明确的雷达工作流中，避免首次用户把后台采集误认为需求研究。

若工作区已有成功或部分完成的需求研究，首页入口区还应提供“查看已完成研究”，优先链接到最近更新且已有未修订研究判断或受控实测证据的真实结果；只有没有可执行证据时才按更新时间回退。该链接只读，不创建任务、不调用模型，帮助用户先判断输出是否有用。列表接口只返回关联判断数量，不暴露完整快照或来源正文。

## 3. 主场景与验收问题

典型输入：“我想做一个真实社会模拟游戏，多个智能体有身份、记忆和目标，能在共享事件下交流和行动，并支持玩家介入。GitHub 上有没有能直接运行的实现？不足时能否改造一个项目或组合几个项目？”

系统必须回答：

1. 用户明确要求什么，系统补充假设是什么，哪些信息仍未知。
2. 找到了哪些真实仓库，检索范围和失败在哪里，为什么值得检查。
3. 哪个完整实现或单项目改造能满足需求；确有缺口时，组合有什么不可替代的分工。
4. 哪些能力有文档支持、固定源码支持或实际运行支持，哪些仍是未知。
5. 下一项最小实验怎么做、依赖什么、观察什么、什么结果会推翻当前建议。

同样的流程应适用于笔记应用、离线工具等其他需求。不能把不同需求套成“三角色、持久记忆、重启恢复”，不能将系统添加的假设标为用户要求。

## 4. 功能要求

### 4.1 需求理解与真实性

原始需求完整持久化。能力逐项标注用户要求或系统假设；缺失信息可以保留，不要求用户先知道仓库名。不凭空指定技术栈、平台、预算、角色数量或额外功能。

模型失效时不伪装语义理解。降级模式只能逐字使用明确引用的检索短语、仓库线索，或中文输入中的 Latin 标识；原需求以未拆解原文保留。无法生成可靠线索时明确停止，并保留可重试输入。不能为了满足输出 schema 而搜索另一个领域。

### 4.2 GitHub 搜索与采集

新研究先验证 GitHub HTTPS 与搜索额度，检查失败不创建假研究或消耗模型调用。初始最多 4 条查询；总计最多 6 次搜索、每次 6 个预览、8 个仓库。短查询分别核查完整实现、领域原生叫法和明确缺口，不把全部验收细节堆成 AND 长句。

只收录实际返回的公开仓库。保存查询、时间、候选、来源、失败和覆盖边界。零结果不证明不存在；未采集不证明没有功能。保持证书校验，不通过关闭 TLS 校验换取成功。

### 4.3 路径比较与反方审查

优先比较直接采用与单项目改造。只有单项目有明确不可覆盖缺口时，才考虑至多 3 个项目的组合。每条路径逐项说明能力覆盖、引用、约束、剩余工作、风险和可证伪实验。

组合必须解释各组件的输入输出、版本、依赖、许可证和状态衔接。未验证的兼容性标记未知。没有证据时允许不推荐，不能强凑路径或虚构工期、成本与运行成功。

审查重点包括最强单项目替代、假设冒充事实、漏掉必须能力、集成成本、来源强度及实验能否推翻建议。同一模型阶段自审标明其边界。

### 4.4 需求驱动的开源实现研究（初版已实现）

需求页 `/research` 提交目标并显示持久进度、查询、采集、评估、审查和失败。保留历史与父子任务关系。可恢复的筛选、评估、补搜或源码分析只继续相应边界，不改旧结论或覆盖失败历史；重复请求通过请求标识幂等处理。

JSON 与离线 HTML 导出保留原需求、来源、固定版本、已知失败、未知项和关联实测。缺少关键材料时明确阻止不完整导出。不把文档中的命令当作产品执行指令。

模型不可用后的资料采集和源码综合标为 `partial`，结论为 `insufficient_evidence`，推荐为空。未拆解原文不能冒充逐项验收能力。无可靠检索线索或无法改写时明确失败，已有材料仍保留。采集结束后可显式恢复比较：恢复必须重新根据原始问题规划，旧降级拆解、筛选理由和空评估不作为语义事实；已有候选、来源和回执复用，缺口补搜仍受剩余预算限制，失败不覆盖父任务。

移动端和窄屏结果页必须把“当前行动摘要”放在关联研究、导出说明和历史材料之前；首屏应能看到结论、阻断因素与下一步。该顺序调整只改变阅读路径，不删除证据、不改变判断，也不把历史材料升级为推荐。验收脚本为 `scripts/verify-demand-first-screen-browser.mjs`。
首页到证据的回归闭环由 `scripts/verify-home-to-evidence-browser.mjs` 验收：从首页只读打开最近成功/部分完成研究，进入当前行动摘要，再跳到相关受控实测并核对成功运行回执；同时检查桌面/390px 无横向溢出、零页面错误和零写请求。该脚本等待异步历史查询完成，并允许同一证据区存在多个入口；它验证导航和证据可见性，不把本地受控实验升级为候选通用可运行或用户收益证明。
结果页和离线交接简报在历史材料之前显示“当前行动摘要”：它从保存快照和当前需求关联的、未被修订的人工/代理判断生成候选、下一步、阻断因素和可证伪验收标准；人工判断仍标为待复核，不把它升级成模型推荐。不得把研究流程（如搜索、固定提交）冒充产品能力。若无有效路径或判断，摘要必须明确停止原因和恢复动作。当前需求判断通过专用读取接口加载，避免为每条历史判断重复校验全部归档产物；全量历史接口也按需求复用同一来源快照。该摘要改善可执行性，但不能替代真实用户任务的时间收益测量。

研究判断可以附带一次任务级对照记录：任务描述、人工基线方法、使用后方法、条件是否可比、前后是否完成、计时方式、任务数、耗时及误留/漏选数量。空白耗时必须保持未记录，不能被解释成零；页面和导出必须明确这只是本次使用记录，不是普遍省时、正确率或市场需求证明。该记录应与判断及其需求材料一起持久化，允许用户回来后补做或修订对照。

结果页在已有候选和可保存判断时必须提供“记录本次任务对照”直达入口。入口打开同一需求的判断表单并自动展开对照字段，但不自动选择候选、不自动保存、不发起模型调用；用户仍需选择候选、填写判断和原文依据后显式保存。入口提示应要求使用同一任务和计时边界，尚未计时必须保留“未记录”。

任务对照表单应提供本地基线/使用后计时器：计时开始、停止和写入字段均在浏览器内完成，停止后填写对应分钟数并切换为实际计时；计时器不得自动提交或调用模型，用户仍需核对可比性、完成状态和引文后显式保存。

结果页的关联判断默认按更新时间展示最近三条当前判断；其余当前判断和已被修订的历史判断必须通过明确入口展开，不能删除或覆盖历史记录。默认折叠只减少阅读负担，不改变导出和存储内容。

每条未被修订且尚未有任务对照的判断旁边必须提供“补充本次任务对照”入口，直接进入该判断的修订表单并展开计时字段；补充保存生成新判断、保留原记录和引文，不能静默覆盖旧判断。

除绑定判断的对照外，产品还必须提供独立的任务对照记录。用户可以在没有研究判断、候选项目或原文引文时，直接记录一次真实任务的人工基线和使用后方法；记录拥有自己的编号、创建时间、可选需求关联、幂等请求、重启读取和 Markdown 导出。独立记录只描述该次任务，不生成推荐、不修改研究结论，也不能被汇总成普遍省时或市场结论。

独立任务对照的保存条件与绑定对照相同：任务描述、两种方法、条件可比性、完成状态和任务数必填；空白耗时保持 `null`，计时方式为 `unmeasured` 时不能携带数值。页面必须提供本地计时器、历史记录和导出入口，存储或网络失败不能把未记录解释成零。

当评估形成候选路径时，结果页必须在详细路径证据之前提供“实现路径总览”：逐项显示直接采用/单项目改造/组合类型、资料支持数量、反方审查状态、运行验证边界和最小实验输入，并能跳到对应完整证据。总览是阅读导航，不得把资料路径写成运行推荐。

### 4.5 固定源码与受控运行

源码续研围绕所选项目和能力保存固定提交、blob、行号、截断及已核验发现。综合失败后可复用这些发现，不能重复采集或改写原证据。

实测分为文档自述、固定源码定位、组件实验、单项目改造运行和多项目集成运行。后一级不能从前一级推断。

已登记实验支持固定命令、无 shell 启动、并发限制、20 分钟上限、持久状态与日志、产物校验和中断处理。需求结果页可直接启动已登记且与当前需求关联的实验，并显示运行中、成功或失败状态；入口只执行 allowlist 中的固定命令，不接受仓库或用户传入命令。未登记实验不自动执行上游任意命令。状态读取失败必须可见，并禁用无法判断是否可运行的启动按钮。

### 4.6 组合方案完成的门槛（尚未通用实现）

组合只有在固定版本和环境下完成依赖安装、分别启动、真实接口互通、共享状态或数据衔接、端到端观察及失败恢复验证后，才能称为“集成验证通过”。

当前候选假设、源码比较和 agent-world 单项目本地改造均不等于上述通用能力。若需要重做多个核心组件，应重新评估单项目替代与研究方向。

### 4.7 受控实测到判断草稿

成功的 allowlist 受控实测必须能回到同一需求的判断表单，减少用户手工抄写证据的成本。入口只在最近一次该实验运行状态为 `succeeded` 时出现，并通过 GitHub 仓库身份与当前需求快照做完整匹配；组合实验存在未匹配仓库时不生成草稿。

草稿预填实测问题、实测结论、下一步、匹配项目和实验归档原文引文，默认标记为代理研究、等待人工复核，且默认判断为 `watch`。草稿是可编辑的本地表单状态，必须由用户修改或确认后点击保存；导航、预填和编辑不能写入研究判断，也不能升级为推荐或改写模型结论。保存仍复用原有引文校验、请求幂等和历史修订机制。

## 2026-10-26 验收边界更新

## 2026-10-27 离线缓存线索能力

当 GitHub 实时 HTTPS 因可信证书链不可用而停止时，产品可以检索已经保存的项目档案，帮助用户继续定位线索。该入口必须明确标为“本地缓存”，返回查询词、每个项目的观察时间和命中的字段；它不能触发 GitHub、模型或写操作，也不能把缓存资料描述为当前仓库状态、候选满足需求或运行成功。

缓存检索使用项目名称、描述和 README 摘录的全文索引。输入词元在进入 FTS5 前全部安全引用，空查询、无有效词元和超长输入拒绝；索引异常时只允许回退到受限的本地 `LIKE` 查询。页面检索失败时仍展示已加载档案，并保留失败边界。

需求研究失败或中断且没有候选时，结果页可以从需求中提取少量有界的中英文能力关键词，打开同一缓存检索入口；用户可以修改关键词。该恢复入口不会伪造新的需求任务、搜索记录或模型结论。

验收条件：`GET /api/v1/projects/search?q=...` 返回 `mode=local_cache`；名称、描述和 README 均可命中；特殊字符不会变成 FTS 运算符；响应和页面显示观察时间；需求失败页可修改关键词并看到缓存候选；Edge 桌面/390px 无横向溢出、零页面错误、零写请求。该能力解决网络失败时的资料可达性，不替代实时 GitHub 研究、依赖安装/启动/组合兼容验证或独立用户价值验证。

每个缓存命中还应直接展示来自项目名称、描述或 README 摘录的有限片段，并提供用户主动点击的原始 GitHub URL，用户可以先判断是否值得打开档案；片段和 URL 仍绑定本地观察时间，不是新的 GitHub 采集或语义推荐。缓存页面必须显示 390px 无横向溢出、零页面错误和零写请求。

缓存证据支持只读下载：`GET /api/v1/projects/search?q=...&limit=...&download=true` 返回与页面相同的 JSON，并设置附件响应头。下载内容必须保留 `mode=local_cache`、原查询词、最新观察时间、候选项目、命中字段和有限证据摘录，供用户交接或离线复核；`download=false` 不得触发附件，非法值应被拒绝。下载仍不是实时 GitHub 结果、推荐、接口兼容证明、运行证明或独立用户收益证据。

新增验收条件：Edge 在需求失败页点击“下载这组缓存证据”后能解析 JSON，字段与页面一致；`download=false` 不带附件头，`download=true` 带附件头，错误布尔值返回 400；整个流程不访问 GitHub、不调用模型、不创建写记录，桌面与 390px 页面无溢出、无页面错误。

首次提交遇到 GitHub 预检失败时，服务按设计不创建研究任务或调用模型；为了避免新用户失去入口，需求输入区必须提供“查看本地缓存线索”的即时恢复按钮。该按钮沿用同一有界关键词提取和只读缓存接口，结果明确标为本地缓存，不能伪装成失败任务或实时搜索。验收脚本 `scripts/verify-demand-offline-first-use.mjs` 通过浏览器注入预检失败，确认仍可看到带证据摘录的候选，390px 无溢出且除故障注入 POST 外没有写请求。

需求输入区同时提供主动的“先查本地缓存”按钮。它不依赖模型配置、GitHub 预检或任务状态，适用于用户明确选择离线线索或当前环境未配置模型的情况；只有在需求达到最小长度后启用。主动查询和失败恢复必须共用同一 `local_cache` 响应与证据边界。

当提交在 GitHub 预检阶段失败时，需求草稿必须留在当前浏览器的本地存储中，刷新页面后可以恢复；草稿只包含用户输入和待重试的父任务标识，不创建服务端任务、不调用模型、不代表搜索成功。输入区应显示“仅保存在此浏览器”的恢复提示，并提供清除入口。浏览器不允许本地存储时仍应可以继续研究，不能把存储异常当作研究失败。

验收条件：输入需求后刷新 `/research` 能恢复草稿；清除入口同时移除本地记录；提交成功后移除草稿；存储不可用时页面仍可编辑和提交；桌面与 390px 无横向溢出、无页面错误。预检失败后的草稿恢复仍不等于实时 GitHub 可用或用户收益证明。

结果页的当前行动摘要在存在候选时必须提供直达“记录本次判断”和“查看或启动受控实测”的入口；入口复用既有保存与 allowlist 实测流程，不接受任意命令。这样用户可以从结论直接进入决定或验证，而不必在历史材料中寻找操作点。

离线缓存候选区必须支持 Markdown 交接简报下载。简报沿用页面和 JSON 的查询、观察时间、扩展词、候选及有限摘录，并明确人工核验步骤和证据边界；它不能生成推荐、运行结论或兼容结论。验收脚本覆盖真实浏览器点击、文件内容、桌面/移动布局、零错误和零写请求。

为减少长需求的漏召回，需求缓存入口在精确多词查询无结果时可以显式启用受限扩展：最多取两个安全词分别检索并合并；响应返回 `expandedQueries`，页面和下载结果都必须显示该扩展状态。项目档案页保持精确 `AND` 查询，不能默认变成宽泛 `OR`。扩展结果仍是本地历史线索，不得升级为推荐、实时状态、可运行证明或兼容证明。

验收条件：`expand=true` 只在需求缓存入口使用；精确查询有结果时不扩展，精确无结果且至少有两个有效词时最多扩展两个词；页面提示扩展词，下载 JSON 的 `expandedQueries` 与页面候选完全一致；浏览器回归无页面错误、无写请求、390px 无横向溢出。验证脚本为 `scripts/verify-demand-cache-expanded-browser.mjs`。

GitHub 预检的证书失败提示必须包含安全恢复动作：管理员通过可信渠道提供 PEM CA bundle，配置 `RADAR_GITHUB_CA_FILE` 后重启；提示必须同时说明不能使用失败连接中的叶证书，也不能关闭 TLS 校验。真实预检失败仍返回 503，不创建任务、不调用模型。

设置页必须显示 GitHub TLS 信任链配置状态：明确区分“使用系统信任链”和“已配置额外 PEM CA bundle”，并说明该状态只描述本地配置，不能证明 GitHub 连接成功。只有 GitHub 预检通过，才可把实时采集标为可用；浏览器回归需覆盖状态区块、边界文案、无页面错误、无写请求和 390px 无横向溢出。
