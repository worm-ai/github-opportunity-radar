# 批量 PDF：本地预处理、独立检查与人工复核的交付方向

研究与实测：2026-10-20；归档复验及备份：2026-10-21凌晨（北京时间）。研究者：代理，待人工复核。产品PRD0.10、DESIGN0.14与schema11未变。

本轮产出一个值得继续核查的工作流假设，并完成两个真实工具的连接实验：给需要批量整理教学/公共文档的团队提供保留目录和已有人工内容的本地预处理、逐份检查报告及人工复核队列。它尚未证明真实文档上的时间收益、采用或付费，不是新的通用PDF编辑器立项。

## 1. 为什么选择这个任务

先通过产品真实搜索比较了PDF无障碍、视频脱敏与本地支持分流。搜索结果本身不证明需求，本地支持查询还混入了网关和网络路由仓库，不能将词面命中当作用户任务。PDF方向有新开源自动打标能力、成熟独立校验器和完整现有方案，适合同时核查机会与反证。

经iii、GitHub官方接口和World2Agent，实际收录：

| 项目 | 本轮角色 | 边界 |
| --- | --- | --- |
| [OpenDataLoader PDF](https://github.com/opendataloader-project/opendataloader-pdf) | 新能力：Apache-2.0开源自动打标，生成Tagged PDF | PDF/UA导出和视觉工作室属于企业功能；README性能/成本数字是供应商自述 |
| [veraPDF](https://github.com/veraPDF/veraPDF-apps) | 成熟组件：独立PDF/UA机械校验 | 双许可MPL/GPL，不是简单标成“许可证未知即不可用”；自动检查不覆盖全部人工语义判断 |
| [ASU PDF Accessibility](https://github.com/ASUCICREPO/PDF_Accessibility) | 现有整体替代与公开问题来源 | 已有AWS编排、Adobe自动打标及修复前后检查；不能声称原先没人做过 |

ASU不作为第三个必须运行的组件。能力组合是OpenDataLoader自动打标＋veraPDF检查，再由薄编排和人工流程组织交付。免费打标不等于免费获得上游企业版全部能力。

## 2. 真实问题和反证

实际重新核查三条讨论，正文与有界评论均取得完整核对：

- [ASU #38](https://github.com/ASUCICREPO/PDF_Accessibility/issues/38)：作者指出子文件夹不被处理、输出层级不保留，称其为批量处理的显著操作负担。这是作者陈述，不能外推到所有机构。
- [ASU #52](https://github.com/ASUCICREPO/PDF_Accessibility/issues/52)：作者要求优先保留人工Alt文本，避免生成结果覆盖已有工作。它也可能只需在原系统增加开关，不能单独支撑一个新公司。
- [ASU #26及评论](https://github.com/ASUCICREPO/PDF_Accessibility/issues/26#issuecomment-4042767031)：另一位参与者报告非表格内容被错误标成表格。另一评论提到在线现成服务；这些是采用线索与替代反证，不是本项目确认的故障率。

进一步读取ASU固定提交 `f4ce18d7fd04acdbb8310aa74b3aa47946210e8c` 的[前置检查](https://github.com/ASUCICREPO/PDF_Accessibility/blob/f4ce18d7fd04acdbb8310aa74b3aa47946210e8c/lambda/pre-remediation-accessibility-checker/main.py)和[后置检查](https://github.com/ASUCICREPO/PDF_Accessibility/blob/f4ce18d7fd04acdbb8310aa74b3aa47946210e8c/lambda/post-remediation-accessibility-checker/main.py)：两者已经调用Adobe检查并保存报告。因此“加一个前后检查器”不是本轮发现的空白；也没有运行ASU云端方案，不能宣称取代后的全面优越性。

## 3. 最小技术实验

运行官方未修改的OpenDataLoader2.5.13和veraPDF1.28.2，固定wheel/JAR并校验SHA-256。当前研究源HEAD与二进制版本不同：实测来源使用各自版本标签，避免把最新源码当作已运行版本。

- OpenDataLoader v2.5.13：`1f1b3e9c67e5052e35082d55e77ab90d2ed25d17`；JAR SHA-256 `48ed84b5bf28e6ba82b8f37771fa5604b1f864bf529543910c8825a68965210c`。
- veraPDF v1.28.2：`77e46c943af719be041f0462307fd43ff7dd41a6`；JAR SHA-256 `687d4d8bcfec48c9f7e931cf78ed061f1eeccfba55d4cdc000ba9b4d8aa46ce6`。选用Maven Central可取得的固定发行版，不宣称是最新版本。
- Python3.12.10、pypdf6.21.1、JBR21.0.6；新依赖只进入隔离实验目录。

四份输入完全人工合成，均为单页。最终一次运行包含一次直接目录基线、两次独立目录转换和两次正常完成的PDF/UA-1校验：

| 检查 | 实测结果 | 可得结论 |
| --- | --- | --- |
| 两部门同名handout.pdf | 原CLI显示处理4份，但平铺同名输出最后只保留部门B标记 | 该固定调用不能直接用于要求保留层级的批量交付 |
| 按相对目录分别转换 | 部门A/B各有Tagged PDF和自己的文本标记，没有另一部门文本 | 小样本的目录隔离和接口连接可行 |
| 部分已有标签及人工Alt | 原输入人工标记，直接重打标后为 `image 1` | 重打标有覆盖已有语义的风险；不等同于ASU问题已被本实验复现 |
| 已有标签先保留 | 分流后输入/输出SHA-256相同 | 本样本原字节保留；不能证明原标签正确 |
| 两份新Tagged PDF | veraPDF实际正常完成，各有5条失败规则、6个失败检查 | 打标成功不能直接当作PDF/UA通过 |
| 纯图像诊断 | 文本为空，进入OCR/人工队列 | 本次没有运行OCR或评价扫描识别质量 |

字体未嵌入、语言及元数据等本来就是合成样本缺少的条件，不能把这些失败全归因于上游、更不能当真实文档错误率。机械校验的“通过”同样不证明正确阅读顺序、图像描述有意义或辅助技术体验良好。没有用补几个字段的方法伪造合规结论。

最初直接调用内部veraPDF CLI缺少解析器初始化，得到配置错误；改用官方Greenfield CLI包装入口后才取得正常校验报告。首个配置失败保留在归档原始日志，不计为文档不合规证据。依赖和版本指引见[实验目录](../../experiments/pdf-accessibility/README.md)。

## 5. 候选业务与下一步

暂保留的定位是面向文档责任团队的交付服务：批量盘点、低成本本地预处理、保护人工成果、逐份追踪和无障碍专家复核。客户买的是减少整理与复核的操作负担以及可追溯交付，这仍是待验证假设；现有上游企业版、Adobe/ASU以及商业工具都是需要认真比较的替代方案。

下一步先用10～20份公开真实教学/公共文档覆盖表格、同名层级、已有人工Alt与扫描件，比较任务时间和漏项；再由有经验的人检查阅读顺序、图像意义和辅助技术体验。没有这些证据前，不扩建编辑器、自动合规服务或销售承诺。若上游小修或现成产品就已足够，停止独立平台化；不会因本次发现覆盖问题而围绕一个局部bug持续扩建。

本轮的价值是把一个笼统“PDF＋AI”点子推进为明确组件分工、现有替代、实际接口、失败边界和可交接复核清单。真实使用、人工节省和付费验证仍未发生。
