# 从原需求找到后续研究与当前判断

第一性原理：用户要决定如何实现需求；研究过程应帮助他找到会改变选择的证据。此前原研究任务 `06fffe22-dc24-4182-bed7-1cc70f60e1c5` 不展示源码续研 `d79a1f02-17c8-4d6d-bf02-1be4e122452f` 的服务反证判断，历史列表却反复显示相同问题。已经做出的技术验证没有顺畅回到原需求的选择流程。

现在结果前部直接展示明确关联任务中最近保存、未被修订的判断，注明来自本次还是关联任务、作者及复核状态。用户从原报告一键进入服务反证判断 `48b24761-5d6a-484c-9b85-2e8edee2616b` 及准确引文；目标区域支持刷新和返回。最新任务的状态与判断独立显示，不将失败当新建议。完整历史模型报告、补充实测和原有修订表单保留。

历史按明确续研和同需求重试分组，本例 6 次关联任务与另一条独立同名任务分开。分组入口优先打开已有终态材料的原始研究，失败任务可继续展开查看。修改需求的重试不加入同组，保留前次任务链接。研究页顶部改成新需求入口，清除重试关联，避免误触雷达扫描。

对抗式审查要求：不能靠问题相同推断共同任务，不能靠窗口外祖先 ID 假装关系完整，不能把较新的代理记录视为优于用户判断。当前只覆盖历史 API 的最近最多 30 条及直接打开的任务；所有未修订判断均可分别查看，来源变化提醒保留，旧后端没有声明判断功能时不调用该接口。服务或记录读取失败明确报错，不伪装成零条判断。
