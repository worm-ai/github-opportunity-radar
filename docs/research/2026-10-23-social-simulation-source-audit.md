## Microverse：有实现基础，不能直接承诺采用

| 疑问 | 源码证据 | 判断及反证 |
| --- | --- | --- |
| 身份、记忆是否参与决策 | `AIAgent.gd` 499～547 行生成场景、人设、状态和任务 prompt；`MemoryManager.gd` 25～61 行将记忆写入 `character_data.memories`；决策状态读取调用格式化记忆 | 有实际数据读取与模型请求，超过 README 关键词证据；不证明模型稳定遵循或长期目标一致 |
| 自主任务是否闭环 | `AIAgent.gd` 1123～1186 行读取 `character_data.tasks`，请求选择移动、交谈、思考或完成；1573～1588 行标记任务完成 | 并非只有聊天。然而 331～361 行展示任务读取独立 `get_meta("tasks")`，默认任务生成也写独立元数据；存在不同容器读写的静态风险，不应直接认定所有任务机制连通 |
| 任务调整是否已实现 | `AIAgent.gd` 1595～1603 行 `_rearrange_task_priorities`、`_add_urgent_task` 明写占位，实际只打印并加记忆；另有默认后备实现 | 不能凭“调整任务”的选项认定 API 决策分支确实更改任务；后备函数存在也不能代替对应调用链核查 |
| 关系会否自行演化 | `GodUI.gd` 473～482 行玩家选择两人后写关系类型与强度；`AIAgent.gd` 285～310 行、`ConversationManager.gd` 读取关系用于 prompt | 在全部 30 个 GDScript 文件中定位到的关系字典赋值来自玩家面板。尚未找到交谈后自动更新关系的调用链；不能由此排除场景资源、其他机制或不同版本，但本版不宜承诺已具备自主关系演化 |
| 共同事件会否改变行动 | 决策读取场景、角色状态和记忆；玩家可改状态/关系；有背景规则模块 | 这些是可改造入口，仍未建立“共同事件 → 多角色状态结算 → 后续行动”的完整证据。事件记忆枚举或 prompt 不等于世界事件规则引擎 |
| 记忆、任务、关系会否持久化 | `project.godot` autoload 指向 `GameSaveManager.gd`；该文件 120～170 行保存位置、部分 AI 属性和人设，237～253 行对应恢复任务属性 | 此保存入口未序列化 `character_data.memories` 或 `relations`，任务使用属性读取而主决策用 metadata。不能把“有存档 UI”当作完整角色状态可恢复；仍须运行保存/重启实验确认实际影响 |

当前研究判断：保留 Microverse 作为 Godot 游戏原型的改造候选，撤回“直接满足全部要求”的理解。先验证状态归属、任务调用与存档，再决定修补范围；源码未运行，以上是静态发现及待证伪风险，不是已复现的运行故障。

## agent-world：需要重新重视的完整替代候选

本轮源码证据比上轮只读 README 更具体：

- `world/relationships.py` 65～104 行实现双向关系分数写入、范围约束及阈值事件；`world/engine.py` 146～167 行按相邻 tick 更新关系，347～373 行交谈向附近角色发事件并增加关系分数。这是实际状态更新调用链，但双向同幅加分是一条简化规则，不能称为真实社会关系模型。
- `world/engine.py` 180～200 行把随机世界事件发给全部活跃角色并保存日志；tick 每 12 次触发一次。它证明事件分发，尚未证明天气等描述改变物理规则、资源或 agent 行动。
- `world/models.py` 有关系与记忆 JSON 存储字段；SDK 提供 `wait_for_event`、`act`、`get_context`、`get_relationships`。字段与接口存在不证明所有行为状态完整恢复，仍需追踪存取及运行检查。
- `sdk/agent.py` 141～162 行示例循环只是收到角色到达事件后问好，没有展示长期目标、记忆检索或自主计划循环。项目中 NPC、外部 agent 和其他入口未全面审查，不把示例的限制推广为全项目没有智能。

当前研究判断：把 agent-world 提升为与 Microverse 并列的单项目验证对象。如果优先共享世界、事件接口及关系机制，先验证它可能比把其他框架接入 Microverse 更合适；如果优先 Godot 游戏呈现，Microverse 仍值得试。没有运行、成本与自主行为证据，尚不能选定赢家。

## 对方向的判断与下一步

方向值得推进：从用户想完成的任务开始，比要求用户先找项目和凑组合更直接。此次补读已将抽象疑问缩小为具体工程风险和替代顺序，说明“搜索之后核查关键行为”应成为产品下一步。

对抗式结论：检索覆盖和模型判断仍会漏掉更合适实现；静态审查不是运行验证，两个仓库都有相关代码也不证明接起来成本更低。暂不建议拼接这两个世界状态系统。应先各自做有界单项目实验，再比较改造或组合。

建议统一实验（尚未执行）：三个角色、一个共享资源和一次玩家介入；记录目标/任务、关系、记忆及行动轨迹，先运行基线，再注入同一可观测世界变化，对比后续动作；保存退出并恢复，核对这些状态是否保留。预算、模型配置和步数须预先记录。只收到事件、生成聊天或打印完成日志不算通过；任一核心状态无法进入后续决策时，记录实际断点，转为改造估计。

产品要能保留父任务、围绕被质疑的能力读固定版本源码，并重新比较替代，而非要求用户从头重跑搜索。该流程、预算和验收已补入 PRD §4.4.6，明确标为待实现。本轮未证明独立使用者省时、项目运行成功或市场需求。
